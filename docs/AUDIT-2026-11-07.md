# Technical audit, 2026-11-07 (session 18)

Scope set by the owner: (1) turn the "Gatekeeper" package-security concept into a measured capability, built inside
RIPPLE from the concept only; (2) measure metadata vs code detection on real data; (3) audit Switch use and the
multi-domain claim; (4) propose a README that only states validated facts.

**Evidence rules for this document.** *Measured* = we ran it in this session and the output is in the repo.
*Inspected* = we read the code. *Source claim* = a file or document says so and we did not re-run it. *Not verified* =
we could not check it. Recommendations are marked as such and are not implemented unless stated.

**Owner instructions that shaped this audit.** The Gatekeeper description was supplied as a concept, with the
instruction not to use external repositories. Before that instruction arrived, one GitHub search was run and one public
repository was cloned to a scratch folder; only its file list was printed, no file was read, the clone was deleted and

### What is incomplete (inspected)
- Squat Watch does **not** poll registries on a schedule. Each install check re-reads the registry for the names in that
  message; the invented-name list and its counts are kept in the room policy (plan) and as an artifact.
- No mission is created automatically from a Switch room message. An install request reaches the pack through the normal
  change submission (API/UI); the observer (`observe.ts`) must be called to record registry data first.
- The approval ledger records "security lead (identity in the audit trail)" in the plan; the person's identity is in the
  `questions.answered_by` column and the audit log, not copied into the ledger row.
- No Switch guardrails-hook endpoint (`/guardrails/check`) exists in RIPPLE. Redaction before delivery is a concept item
  only.

### Claimed but not verified
- No part of the package-gate pack has run against a Switch server. This sandbox had no Switch server.
- Earlier sessions' Switch evidence (`docs/evidence/switch-live*.json`) was not re-run in this session.
- The PyPI reference list is authored, not download-ranked.

### Technically unsafe or risky (inspected)
- The observer downloads archives from registry URLs into memory. It never writes, extracts or executes them, caps an
  archive at 30 MB, caps decompression at 200 MB and each entry at 8 MB. A decompression bomb inside those limits still
  costs memory and CPU; run the observer in a worker with its own memory limit in production. *Recommendation.*
- `clean` from the inspector means "no rule matched". The pack's text says so, and a flagged package without a code
  reading is reported as "not inspected", never clean.
- The static rules are regular expressions over text. Obfuscated payloads, binaries, and code fetched at run time are
  invisible to them by design (measured: 13% of the still-served npm malware has no JavaScript at all).

|---|---|---|---|---|---|---|

## G. Final verdict

- **Technically credible?** Yes for what is now claimed: the checks, the pack and the engine journey are tested, and the
  detection numbers come from a reproducible harness on real registry data with a frozen-rules held-out split.
- **Is security performance demonstrated?** For npm metadata, yes (93.9% at first publish, 58.8% across the live
  window, with a measured cost of 15.4% on fresh legitimate packages). Static code reading is **not** shown to be strong
  on this population (npm 3.2%, PyPI 50%), and the concept project's own numbers remain unverified.
- **Strongest differentiator.** A measured, time-aware replay of registry metadata (npm placeholders keep timestamps),
  joined to a human gate that binds each decision to an exact version and re-verifies the posted install line.
- **Biggest weakness.** Malicious versions of established packages (32.7% caught by metadata) and fresh legitimate
  packages (15.4% npm / 43.8% PyPI flagged): the gate is strongest exactly where the threat is easiest.
- **Hardest to replicate.** The labelled, version-bound decision ledger plus a benchmark that others can rerun offline
  from committed data and that publishes its own false-positive cost.
- **Build next.** Improvement 1 (version-diff inspection), then 2 (cross-mission links).
