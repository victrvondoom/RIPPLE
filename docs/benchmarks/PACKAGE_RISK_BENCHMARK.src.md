# Package-risk benchmark: metadata vs static code vs combined (npm and PyPI)

System measured: RIPPLE's own `src/server/capabilities/pkgguard` (the checks used by the `package-gate` pack).
Harness: `bench/pkgguard/` (method and commands in `bench/pkgguard/README.md`). Raw metrics:
`bench/pkgguard/results/metrics-heldout.json` (reported, generated {{raw:generatedAt}}) and `metrics-tune.json`.
**Every number in this document is filled in from those files by `bench/pkgguard/08-render-docs.ts`; the source text is
`PACKAGE_RISK_BENCHMARK.src.md`.** The appendix tables are generated by `07-tables.ts`.

**Labels.** *Measured* = computed by the harness. *Source claim* = something a data source states (for example OSV's
report time). *Inference* = our reading of a measured number. *Recommendation* = a suggestion, not implemented unless
the text says so.

**What this is not.** It does not measure the separate "Gatekeeper" project whose description the owner supplied as a
concept. By the owner's instruction no external repository was used, so Gatekeeper's published numbers (npm 60.5% /
PyPI 84% on Datadog's dataset) were **not** verified or reproduced and cannot be compared one-for-one with these.

## 3. Method

- **Historical metadata, not reconstructed.** npm replaces removed malware with a `0.0.1-security` placeholder but keeps
  the original `time` map (version → publish time). The replay rebuilds what an installer saw at a moment *t* using only
  versions published by *t*. Fields npm no longer has (install scripts of removed versions, historical downloads) are
  unknown, never guessed. Moments: the first malicious publish, the first report, and 11 evenly spaced moments from the
  first malicious publish to npm's takedown (or to the snapshot, if still live).
- **Rules (fixed before any data was read).** `metadata.ts`: flag when the name is a lookalike, OR the version looks like
  dependency confusion (major ≥ 90 with ≤ 3 releases), OR (younger than 30 days AND ≤ 2 releases), OR (younger than 30
  days AND an install script). `names.ts`: optimal-string-alignment distance 1 (names ≥ 4 chars) or 2 (≥ 9 chars),
  separator, scope and homoglyph confusion against the reference lists ({{n:rules.referenceSizes.npm}} npm names by weekly
  downloads; {{n:rules.referenceSizes.pypi}} authored PyPI names). `inspect.ts`: weighted rules; "review" at score ≥ 4,
  "malicious-looking" at ≥ 7.
- **Leakage control.** 30/70 tuning/held-out split by `sha256(ecosystem:name)`. Metadata and name thresholds were never
  changed. Code rules went from `inspect@1` (written blind) to `inspect@2` on the tuning split only and were frozen in
  commit `52239ba` before the held-out split was first evaluated.
- **Safety.** No package was installed, imported, extracted to disk or run. Archives were read into memory as text and
  dropped; only rule ids, files and line numbers were stored.
- **Statistics.** Wilson 95% intervals. Precision and F1 are reported at each comparison's own mix and are not
  prevalence-adjusted; false-positive rates are the numbers to carry to a real team.

## 4. Findings (measured, with our reading)

1. **On npm, metadata is the detector; code reading adds little in this population.** At the first malicious publish
   the metadata rules flag {{pct:E2_npm_metadata.confusion.atPublish_vs_allControls.recall}}; code reading flags
   {{pct:E3_code.npm.atReview.vsAllBenign.recall}} of the still-downloadable archives, and only
   {{n:E4_npm_combined.atReview.malicious.codeOnly}} of {{n:E4_npm_combined.atReview.malicious.n}} were caught by code
   alone. Recall at review by reporting source: Amazon Inspector bulk feed only
   {{pctv:E3_code.npm.recallBySource.amazonInspectorOnly.pct}} ({{n:E3_code.npm.recallBySource.amazonInspectorOnly.hits}}/{{n:E3_code.npm.recallBySource.amazonInspectorOnly.n}}),
   other sources {{pctv:E3_code.npm.recallBySource.otherSources.pct}} ({{n:E3_code.npm.recallBySource.otherSources.hits}}/{{n:E3_code.npm.recallBySource.otherSources.n}}).
   *Inference:* most npm entries in OSV are brand-new, one-version packages (dependency-confusion probes, token-farming
   spam, bulk-reported floods), many with little or no code.
2. **The "new package" signal decays.** Detection is {{pct:E2_npm_metadata.confusion.atPublish_vs_allControls.recall}} at
   the first malicious publish, {{pctv:E2_npm_metadata.liveWindow.byMoment.1.pct}} one tenth into the live window and
   {{pctv:E2_npm_metadata.liveWindow.byMoment.10.pct}} at takedown (window median {{raw:E2_npm_metadata.liveWindow.windowDays.median}}
   days, p90 {{raw:E2_npm_metadata.liveWindow.windowDays.p90}} days).
3. **The cost is paid by fresh legitimate packages.** {{pct:E2_npm_metadata.confusion.atPublish_vs_popular.fpr}} of popular npm
   packages are flagged, but {{pct:E2_npm_metadata.confusion.atPublish_vs_fresh.fpr}} of npm packages under 30 days old and
   {{pctv:E2b_pypi_metadata.controls.fresh.COMPOSITE.pct}} of fresh PyPI projects are. *Inference:* the rule is usable as "ask a
   person", not as a silent block.
4. **Typosquat detection is a minor channel.** npm: {{pct:E1_names.npm.lookalike.recall}} of malicious names vs
   {{pct:E1_names.npm.lookalike.fpr}} of legitimate names. PyPI: {{pct:E1_names.pypi.lookalike.recall}} at
   {{pct:E1_names.pypi.lookalike.fpr}} false alarms (most-imitated targets in T1).
5. **Malicious versions of existing packages are the blind spot.** {{pctv:E2_npm_metadata.newlyRegistered.existingPackageGotMaliciousVersion.pct}}
   of npm malicious packages were existing packages that received a malicious version (for example `fsevents`
   1.0.0–1.2.10, which had 15 earlier versions); the metadata composite flags {{pctv:E2_npm_metadata.newlyRegistered.existingDetected.pct}}
   of them.
6. **PyPI code reading works better than npm.** {{pct:E3_code.pypi.atReview.vsAllBenign.recall}} at review
   ({{pctv:E3_code.pypi.recallBySource.otherSources.pct}} of the {{n:E3_code.pypi.recallBySource.otherSources.n}} samples reported by
   sources other than Amazon Inspector), with {{pct:E3_code.pypi.atReview.vsAllBenign.fpr}} false alarms
   ({{pctv:E3_code.pypi.atReview.fpr_popular.pct}} on the well-known list). At score ≥ 7:
   {{pct:E3_code.pypi.atMalicious.vsAllBenign.recall}} with {{pct:E3_code.pypi.atMalicious.vsAllBenign.fpr}} false alarms.
7. **Downloads are not a usable signal from this sandbox.** Historical counts for removed packages were not reachable
   (`api.npmjs.org`, `pypistats.org` and `api.deps.dev` were refused by the network policy), and snapshot counts of
   still-live malware are inflated by mirrors and scanners (T8).

## 7. Limitations and disclosed corrections

- PyPI metadata for removed projects is unrecoverable; PyPI metadata numbers cover only still-live reported projects.
- The live-window average weights every moment equally; real installs are not uniform in time.
- Download counts are snapshot values for live packages only.
- The PyPI reference and popular lists are an authored list of well-known projects, not a download ranking.
- npm controls come from search results, which favour packages matching common terms.
- OSV includes bulk-reported spam; no record was relabelled. Results by reporting source are in T9.
- Slopsquatting (registration of names coding agents invent) could not be measured: no corpus of agent-invented names
  with registration outcomes was available. The live Squat Watch records such registrations from now on.
- **Corrections made after the first held-out evaluation (no detection rule or threshold changed):** (a) an OSV bounded
  range without a version list was read as "all versions" (2 of 3,000 sampled npm records); (b) the PyPI all-controls
  comparison counted some fresh projects twice; (c) source and no-code breakdowns were added; (d) session 19: withdrawn
  OSV reports were not skipped when excluding names from the controls (this removed `react`, whose report MAL-2024-2929
  was withdrawn), and the npm crawl missed top packages that matched no authored term (`lodash`); the crawl now adds
  name-stem queries and every downstream step was re-run. The numbers above are from that re-run.

## 8. Recommendations supported by these numbers

1. **Metadata as the first gate, with a human decision, not a block** (findings 1 and 3). The package-gate pack does this.
2. **Version-diff check for updates to established packages** (finding 5): compare install scripts, network code and
   files with the previous version. *Not built.*
3. **Test a "burst" rule on a fresh split** (§6): many versions within hours of creation. *Hypothesis only.*
4. **Advisory lookup at install time** (finding 2): only {{pctv:E2_npm_metadata.timing.reportedBefore7Days.pct}} of reports
   appear within 7 days of the malicious publish, so it helps late installs but cannot replace the age rule.
5. **Do not headline typosquat detection on npm** (finding 4).

## 9. Reproduce

```bash
npm ci
npx tsx bench/pkgguard/05-evaluate.ts heldout   # offline: recomputes every metric from the committed data/*.jsonl.gz
npx tsx bench/pkgguard/07-tables.ts heldout
npx tsx bench/pkgguard/08-render-docs.ts        # re-renders this report and the README / audit blocks
```

so a re-collection is a new snapshot.
